# Adoption

This page shows how Jarette's Box (JB) and heb-stack (HS) move onto this specification without rewriting how they work. Both keep writing capabilities in TypeScript with Effect. What changes is that each one produces its catalog as a document at build time, and each surface follows its binding.

## What stays

- **Capability definitions in code.** Both keep `defineCapability` with Effect Schema input, output and error codecs. The catalog is generated from those definitions at build time and checked. It is the contract that every other implementation is built against: a Swift app, a Kotlin app, the conformance kit.
- **Target names.** Targets are the application's own choice, so JB keeps `application` and HS keeps `web` and `rpc`.
- **Handles, owners and the root.** The [TypeScript binding](bindings/typescript.md) is the handle shape that both kernels already have. Effect, XState, owners, scopes and lazy loading stay as they are.
- **The compact manifest encoding in JB.** It stays as a way of carrying the `application` view to the page.

## Shared steps

1. **Generate `acidcat.catalog.json` and commit it.** Extend the existing manifest generator, walking the same `definitions` tree:
   - write `acidcat: "0.1"` and a `targets` map;
   - for each leaf, write `description`, `audience`, `input` and `output` from the program's codecs;
   - split the error union into `failures` keyed by each variant's `_tag` literal. A capability whose error is `never` gets no `failures`;
   - move every schema's own `$defs` up into the catalog's [`$defs`](catalog.md#types), and turn schemas that repeat into shared types.

   [`adoption/jarettes-box/generate-acid-cat-catalog-export.ts`](../adoption/jarettes-box/generate-acid-cat-catalog-export.ts) does all of this for JB, using JB's own `manifestSchema`. HS's generator follows the same steps.
2. **Check the catalog.** In the existing conformance gate, fail when the catalog is stale, whether it is committed or regenerated by the build. Put it in [canonical form](catalog.md#canonical-form) with `acid-cat format --write`, and validate it with `acid-cat check`, both from the [`acidcat` toolchain](../packages/cli/README.md).
3. **Publish views.** Each binding publishes exactly its target's view, from the definitions it already has. JB's page may keep loading its precomputed WebMCP manifest on first use, now derived from the `application` view.
4. **Give call failures their kind.** In the executor, set `kind` on the errors that `invokeExternal` throws (`cancelled`, `unavailable`, `invalid-input`, `internal`), and map them in each adapter, as each binding states.
5. **MCP.** Wrap failures as `{ "ok": false, "error" }`, return call failures with `{ "kind", "message" }`, publish `outputSchema` and `readOnlyHint`, pass the request's signal to the call, and screen the media type and UTF-8.

### Does the architecture suit JB?

Yes. JB keeps how it writes capabilities and how it runs them. It gains a checked contract, and loses nothing it relies on. These findings come from running JB's own code at `bartering@8e8653273eb5`:

- **Code-first works.** The exporter derives the catalog from JB's Effect definitions with JB's own `manifestSchema`. The result conforms, is in canonical form, and gives correct views: `mcp` sees its 3 capabilities in 26 KB, and `cli` sees its 2.
- **It fits JB's existing gates.** JB already generates a manifest at build time and fails its conformance test when the manifest is stale. That gate becomes "the catalog is fresh and `acid-cat check` passes". JB chose not to commit generated manifests, and the specification allows that: a catalog that the build regenerates reproducibly is versioned with the application.
- **Nothing changes at runtime.** JB's handles already are the [TypeScript binding](bindings/typescript.md). No program has to read the catalog. JB's page may keep loading its compact WebMCP manifest on first use, which is now the `application` view in a transport encoding.
- **Growing the tool surfaces stays one declaration at a time.** Reaching the CLI or MCP is still a matter of adding a target to a capability's audience, as it is today.
- **The binding changes are small and local:** the `kind` of call failures in the executor; the outcome shapes in the MCP toolkit; commands generated from ids, and exit codes, in the CLI; committing only successful WebMCP passes.
- **The design can now take advantage of build time.** JB's MCP Worker converts Effect schemas to JSON Schema when it handles a request. With views computed at build time it can publish precomputed, bundled tool schemas instead. This is optional.
- **The gaps are in what JB declares, not in the format.** Unnamed types, free-text failure codes, no `readOnly`, unmarked attachment handles and few field descriptions are listed in the pull request below.

### Exporting JB today

At `bartering@8e8653273eb5` the exporter produces a conforming catalog: 99 capabilities in 270 KB, with 106 shared types. After `acid-cat format` it is in canonical form, and `acid-cat check` passes. Without shared types the same catalog is 2.6 MB, because 22 capabilities each repeat the 90 KB workbench schema.

### Later: a pull request to JB

Once the specification is stable, one pull request to JB improves what its catalog says. None of these items blocks adoption:

- **Name the shared types.** Give the schemas that repeat, such as the workbench, sailors, ships and map items, an Effect `identifier`, so that `$defs` holds `Workbench` instead of `BarteringWorkbenchInspectOutputWorkbench`.
- **List the failures.** `BarteringFailure`, `ShipFailure` and the other domain failures carry a free-text `code`, so neither an agent nor generated code can tell which failures can happen. Give each one its own tag, or at least make `code` an enum.
- **Mark reads.** Add `readOnly` to `defineCapability`, and set it on the reads. 36 ids end in verbs such as `inspect`, `list` or `search`.
- **Mark attachment handles** with `format: acidcat-attachment` in the three capabilities that take screenshots.
- **Describe the fields.** The schemas carry about 36,000 typed nodes and 87 descriptions, so agents see types with little explanation.
- **Reconsider union inputs.** 17 of the 99 inputs choose between shapes, which the CLI can only reach through `call`.
- **Declare state.** JB's snapshots exist only in TypeScript. Declaring `state` would let other bindings observe them.

JB's own requirements stay JB's own checks: every capability reaches `application`; `cli` and `mcp` are strict subsets; every array has `maxItems`; Product Promises cover every id. The specification allows all of them and requires none of them.

The capnweb API can keep its typed `check` and `next` methods as an application binding (`hs:capnweb`). Moving to the [HTTP binding](bindings/http.md) later is optional.

## Order

1. Both repositories generate, commit and check their catalogs. Nothing else changes yet, and both stay green.
2. Each binding change lands behind `acid-cat conform`, one binding at a time.
3. Once both repositories pass the kit, either can replace its kernel with [`@acid-cat/core-effect`](../packages/README.md#two-cores).
