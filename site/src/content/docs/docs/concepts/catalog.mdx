The **catalog** is the contract of an application. It is one JSON document that lists:

- the **capabilities**: the operations that a client can do;
- the **events**: the things that happen, which clients can follow;
- the **targets**: the groups of clients, and the bindings that serve each group.

Each application has one catalog. Every surface comes from it.

## The top of a catalog

A catalog starts with the members that describe the catalog itself. This is the start of the catalog of the air conditioner, in each source and in the JSON that each source writes:

<CatalogExample header />

- `acidcat` is the version of the AcidCat specification that the catalog follows: `"0.1"`. It is not the version of your application, and not the version of the catalog. It is required. The catalog library writes it, so a source does not set it.
- `title` is a name for people. It is optional.
- `description` tells what the application does. It is optional.

The Pkl tab shows the example in the repository, which amends the module `Catalog.pkl` by its path. A project amends the published package. [Document](/spec/catalog/#document) in the specification lists these members.

## The members of a catalog

| Member | Required | Value |
| --- | --- | --- |
| `acidcat` | Yes | The version of the specification that the catalog follows: `"0.1"` |
| `title` | No | A name for people |
| `description` | No | What the application does |
| `targets` | Yes | The targets, by name |
| `$defs` | No | The shared types, by name |
| `capabilities` | Yes | The capabilities, by id |
| `events` | No | The events, by id |

## Ids

Each capability and each event has an **id**: two or more segments, with a dot between them, for example `aircon.power.set`. Each surface makes its names from the id. `aircon.power.set` becomes the command `aircon power set` and the HTTP route `POST /capabilities/aircon.power.set`.

Capabilities and events share one set of ids. An id is a name, not a version. To give an operation a new meaning, give it a new id.

## Shared types

Put a schema that you use in more than one place in `$defs`, and refer to it with `$ref`. In the air conditioner, `Status` is the output and the state of `aircon.status.get`, and the payload of `aircon.status.changed`. Each source declares the type one time, and uses the reference that it gets back:

<CatalogExample type="Status" capability="aircon.status.get" />

Each schema in a catalog is JSON Schema 2020-12.

## Build time, not run time

The catalog is a build-time file. Keep it with the source code, and check it in your build with `acid-cat check`. A program does not read the catalog at run time: it uses its own code. Each binding must agree with the catalog.

## Write a source, not JSON

The JSON document is long, and a text editor does not check its rules. Write a source, and let a tool write the JSON:

- a [Pkl](https://pkl-lang.org) module;
- a program that uses the catalog library of your language;
- the code of the application, when a core writes the catalog from it.

Every tool writes the same bytes for the same catalog: the **canonical form**. [Write a catalog](/docs/guides/write-a-catalog/) shows each source.
