# The traps of each binding

The documents of the bindings are at https://github.com/Hebilicious/acidcat/tree/main/spec/bindings.

## MCP through HTTP

- One URL, `/mcp`. Revision `2026-07-28`: each request is its own session. The server keeps no state between requests, except poll leases and webhook subscriptions.
- The server rejects origins that are not in `allowedOrigins`. A request with no `Origin` header is accepted.
- An unavailable capability is not listed, and a call to it gets the same answer as an unknown tool.
- The server checks the headers of each request against its body: `Mcp-Method`, `Mcp-Name` for `tools/call` and the `events/*` requests that name an event, and an `Mcp-Param-{Name}` header for each input property with `"x-mcp-header": "{Name}"` that has a value. A mismatch gets 400 and `-32020`. Annotate only a property with `type` `string`, `boolean` or `integer` that a chain of `properties` reaches from the root, with no `items`, `anyOf`, `allOf`, `$ref` or other keyword between them, and never a property that holds a secret: intermediaries see the headers. The value is an HTTP token, unique in the input schema without regard to case. `acid-cat check` rejects an annotation that breaks these [rules](https://github.com/Hebilicious/acidcat/blob/main/spec/bindings/mcp.md#header-annotations), because MCP clients through HTTP remove that tool or event from their list. In core-ts: `z.string().meta({ "x-mcp-header": "Region" })`. In core-effect: `Schema.String.annotate({ "x-mcp-header": "Region" })`, before any check; for an integer, `Schema.Number.annotate({ "x-mcp-header": "Count" }).check(Schema.isInt())`. In core-rust: `#[schemars(extend("x-mcp-header" = "Region"))]`. In a catalog source: the member `x-mcp-header` of the property (`` `x-mcp-header` = "Region" `` in Pkl). The official MCP client and `Mcp.withHandshake`/`mcpHandshake` send the headers for you.
- Events use the MCP events extension, only in revision `2026-07-28`, and only when the view has events. A client with the `initialize` handshake gets no events.
  - Push: the answer to `events/stream` is a stream of server-sent events. The client can suggest `heartbeatMs`. The server grants it between 1000 and 60000 ms, or uses the heartbeat option of the deployment (default 15000) when there is no suggestion, and gives the grant in `heartbeatMs` on each `notifications/events/active`. An invalid suggestion gets `-32602`.
  - Poll: `events/poll` reads a lease, which holds the subscription between polls in a session of its own. A lease ends when it gets no poll for 5 minutes. Keep the cursor of each result, and give it to the next poll.
  - Webhook: off by default. The deployment turns it on, and gives the identity of each client (the principal). In core-ts: the options `webhooks: webhookDelivery(…)` (from `@acid-cat/core-ts/node`) and `principal(request)` of `mcpHandler`. In core-effect: the options `webhooks: { sender: NodeWebhook.sender(…) }` and `principal` of the MCP binding. In core-rust: `McpOptions::webhooks` and `McpOptions::principal`. With webhook delivery off, `events/subscribe` and `events/unsubscribe` answer `Unsupported`. The callback URL must use `https`, must agree to get deliveries (a `verification` message, or the allowlist), and must resolve to a globally routable address. In tests with a local receiver, set `allowPrivateNetworks` and give its certificate in `ca`.
- Server Card: each MCP server through HTTP serves one at `<MCP URL>/server-card` by default. The default name is the labels of the host in reverse order, `/`, and the server `name` (`com.example.aircon/aircon` at `aircon.example.com`, `local/aircon` at an IP address), with the host in punycode (`example.xn--bcher-kva/aircon` at `bücher.example`); the default description is the catalog description, shortened to 100 characters. Give a registry name in reverse-DNS form (`com.example/aircon`), a `description` of 1 to 100 characters, or a `url`: an absolute `http` or `https` URL with a host. core-ts: `serverCard: { name }` of `mcpHandler`, `serverCard: false` to turn it off. core-effect: the same option of `Mcp.toWebHandler` and `Mcp.withEvents`. core-rust: `McpOptions::server_card: Some(ServerCard::named(name))`, `None` to turn it off. `Mcp.withEvents` serves the card of your own server: at each card request it sends `server/discover` to your server, with no credentials, and takes the version from it. The default description is then the `instructions` of your server, else the catalog description, else the `name` of its `serverInfo`. If `server/discover` fails (for example, because your server requires credentials), has no `serverInfo` with a `name` and a `version`, or gives a version range, the card request gets 502; give `serverCard: false` to turn the card off. Behind a platform that ends TLS, give the `https` URL in `url`, or the card gives the `http` URL that the server gets. The card gives the version of the server, so with the card on the version must be one version, not a range such as `^1.2.3` or `1.x`. The card name is the registry name; the `name` of the server is the runtime `serverInfo.name`. A given value that breaks these rules makes the server fail when it starts; a default never does. Put `mcpHandshake`/`Mcp.withHandshake` in front, so that the card also gives the revisions of the handshake.
- Webhook signing keys: give Ed25519 private JWKs with a `kid` (`signingKeys` in core-ts and core-effect, `WebhookOptions::signing_keys` in core-rust) so that each delivery and verification also has a `v1a,` signature per key. The card gives only the public keys. Give the new key beside the old one to rotate. `egressIpRanges` (`egress_ip_ranges`) puts the CIDR ranges of the server in the card. Signing keys or egress ranges with the Server Card off make the server fail when it starts, because a receiver gets them only from the card. Keep the private keys in a secret store, never in the code. Serve the card through HTTPS in production, and put nothing private in it.
- The principal is part of the key of a poll lease and of a webhook subscription. Give it from a verified identity, never from a header that the client chooses.
- Poll leases and webhook subscriptions are the only state between requests. They are soft: after a restart, clients start again with their cursors.
- Keep the network safety of the webhook sender on: it connects only to globally routable addresses. Allow private networks only in tests.

## Serve MCP and HTTP on a network

- The TypeScript cores give web handlers, `(request: Request) => Promise<Response>`. The host serves them. On Node.js, use the server of the core: `serve` from `@acid-cat/core-ts/node`, or `NodeServer.serve` and `NodeServer.layer` from `@acid-cat/core-effect/NodeServer`. On Bun, Deno and Cloudflare Workers, give the handler to the server of the runtime. The Rust core gives handlers that implement `remote::Handler`, and `remote::serve(address, routes)` serves them with hyper.
- Authenticate each request in the context of the request: `createContext(request)` and `refuse` in core-ts, a per-request layer with `Remote.IncomingRequest` and `Remote.refuse` in core-effect, `with_request_context` and `Refusal` in core-rust. The function reads the headers, and refuses a request with no valid caller: the answer has its status (400 to 599) and the body `{ "message" }`, and no session opens. Through MCP, also give the `principal` from the same caller: a poll lease is keyed by the principal, so with no principal two callers share one lease. In core-effect, `Mcp.withEvents` refuses only the requests of the events extension; your own MCP server authenticates the others. The capabilities read the caller from the context.
- `serve` from `@acid-cat/cli` is for tests only. It listens on `127.0.0.1`, on a free port.
- The server of a core is plain HTTP/1.1, on `127.0.0.1:3000` by default. In a container, set `hostname` to `0.0.0.0` or `::`, or the platform cannot connect.
- End TLS in the platform, before the server: a load balancer, the ingress of a Kubernetes cluster with cert-manager, or a tunnel. The platform sends plain HTTP to the server. Do not write a TLS proxy in front of the server. When TLS must reach the process, give the handler to a library that serves HTTPS, for example srvx, in place of the server of the core.

## MCP through stdio

- The process is one session. Standard output carries only MCP messages. Write logs to standard error.
- The server tells the client when the set of available tools changes (`notifications/tools/list_changed`).
- When standard input ends, the server cancels the calls in progress, ends each subscription as complete, and exits.
- The messages of each `events/stream` request go to standard output, with the id of the request in `_meta["io.modelcontextprotocol/subscriptionId"]`. `notifications/cancelled` with that id cancels the subscription.
- `events/poll` serves poll leases. When standard input ends, the leases end. Webhook delivery is not served through stdio.

## HTTP

- `GET {base}/capabilities` lists the view with availability. `POST {base}/capabilities/{id}` calls a capability with the input as the body.
- A result has the status 200. A call failure has its own status: 404, 422, 503, 409 or 500.
- `GET {base}/events` lists the events. `POST {base}/events/{id}` gives a stream of server-sent events in the framing of graphql-sse: `event: next`, then `event: complete` or `event: error`. A failure before the first occurrence is a JSON call failure with its status. `Last-Event-ID` gives the cursor. Behind a proxy, turn off the buffering of responses, or the client gets no occurrence until the buffer is full.

## Command line

- Each capability is a command: `aircon.power.set` gives `aircon power set`. Each input property is a flag. Give a value that starts with `-` as `--name=value`: `--key=--cursor`.
- A shared prefix only contains other commands. An id must not be the start of another id: with `aircon.status` and `aircon.status.get`, the command line stops with an error when it starts.
- `--help` after a command, an alias or `watch <id>` writes `Usage: ` and the usage, an empty line, and the description, with exit code 0. `--help` after a shared prefix writes `Commands:`, then two spaces and the usage of each command under it, in the order of `list`, with exit code 0. A shared prefix alone, or with arguments that are not `--help` and are not the path of a command, such as `aircon status --on`, writes the same list to standard error, with exit code 2. Each core does it, and `acid-cat conform --cli` checks it.
- An id has two or more segments, so a command of a capability has two or more words. For a shorter form, give the `cli` target [aliases](https://github.com/Hebilicious/acidcat/blob/main/spec/bindings/cli.md#aliases) in the catalog: `options: { cli: { aliases: { status: { capability: "aircon.status.get" }, "--on": { capability: "aircon.power.set", input: { on: true } } } } }`. A command alias is one word (`aircon status`), or two words with one space between them (`aircon fan high`). A flag alias is `--` and one word (`aircon --on`). The command aliases with the same first word are a group: `fan`, `fan auto` and `fan high`. The first two arguments that are the name of a two-word alias run it. If not, the one-word alias of the group runs with the other arguments, but a second argument that is a word, such as `fan medium`, is an unknown command with exit code 2. A group with no one-word alias is like a shared prefix: its first word alone is an unknown command. The name of a command alias can be a shared prefix of commands (`inbox` for `inbox.adopt` and `inbox.list`, or `aircon power` for `aircon.power.set`): it is then the prefix default of that prefix, and the commands under it keep their paths. Thus the ids need no extra first word, such as `sync` in `sync.inbox.adopt`, to keep the first word free for an alias. Arguments that start with the path of a command run the command. A word after a prefix default that names no command, such as `inbox nope`, is an unknown command with exit code 2. The fixed `input` is always sent, and its properties are not flags. The provider validates it with the rest of the input of each call. An alias of a capability whose input schema has no `properties` takes the input as JSON text, as `call` does. The first word of a command alias must not be `call`, `list`, `watch`, or a command of the application, and the name of a command alias must not be the path of a capability command, such as `inbox adopt`. A flag alias must not be `--help`, `--version` or another flag of the program. A command of the application must not have the first word of a command alias. Its capability must be in the view, and the target must have the binding `cli`. An alias has `capability` or `event`, an optional `input`, and only other members that start with `x-`. `acid-cat check` rejects an alias that breaks a rule, and the command line stops when it starts. In the code of a core, give the aliases from the capability or event objects, so that the id and the fixed input are typed: `cli: { aliases: { status: cliAliasDefault(statusGet), "--on": cliAlias(powerSet, { on: true }) } }` in core-ts, `App.alias` and `App.aliasDefault` in core-effect, and `App::cli_aliases(target, CliAliases::new().alias_default("status", &status_get).alias_with("--on", &power_set, Power { on: true }))` in core-rust, where the fixed input is a value of the input type and a property that is `None` stays a flag. In Pkl, the member `cli` of a target has the classes `CliOptions` and `CliAlias`. An alias can also name an event: `follow: { event: "aircon.status.changed" }` makes `aircon follow` the same as `aircon watch aircon.status.changed`, with `--cursor` and `--max-age-ms`. `options.cli.default` names a command alias, of one or two words, that runs when the command line gets no command: with no arguments, or when the first argument is a flag that is not a flag alias or a flag of the program. Then `aircon` alone, or `aircon --flag`, runs it, and `--help` still writes the help. A flag of the default alias must not have the name of a flag alias. `list` gives the usage of the aliases of each capability and each event in `aliases`.
- An array of simple items is a repeated flag: `--days mon --days fri`, or `--days '["mon","fri"]'`.
- The command line ignores a first argument `--`, which package runners such as `pnpm` and `npx` pass to it: `pnpm exec aircon -- status` runs `aircon status`. Each core does it.
- Exit codes: 0 for a value, 1 for a failure, 2 unknown, 3 invalid input, 4 unavailable, 5 internal, 130 cancelled.
- An interrupt (`SIGINT`) cancels the call or the subscription. The main program of each core (`cliMain`, `NodeCli.main` and `NodeCli.runCommand`, `cli_main` and `run_cli_process`) exits with 130 one second after the interrupt if the run has not ended, and at once at a second interrupt. Still stop each capability on its signal: the process does not wait for a capability that ignores it.
- `watch <id>` subscribes to an event, and writes each occurrence as JSON on one line. It exits with 0 when the subscription is complete, 130 after an interrupt, and 5 after `internal`. An interrupt writes nothing to standard error, also when it comes before the subscription starts. `list` gives each item a `kind`: `capability` or `event`. No command can have the name `watch`. Write logs to standard error, or they break the lines of JSON.
- `watch <id> --cursor <cursor> --max-age-ms <integer>` resumes after the cursor of an earlier occurrence. No input property of an event can be named `cursor` or `max-age-ms`: the command line stops with an error when it starts.
- The command line can run on another machine than the application ([Server](https://github.com/Hebilicious/acidcat/blob/main/spec/bindings/cli.md#server)): it sends each call and each subscription to the HTTP binding of a server. core-ts: `remote: httpClient(url, { headers })` in the options of the command line. core-effect: `remote: Http.client(url, { headers })` in `Cli.Options`. core-rust: `CliOptions::remote(HttpClient::new(url)?.header(…)?)`. The commands still come from the view in the program. Serve that HTTP binding with the target of the command line, so that both have the same view. Give a token in a header when the server checks one: the command line never writes it.
- The command line writes JSON. A result, a failure and the output of `list` are one line of JSON when standard output is not a terminal, and have an indent of 2 on a terminal: `io.pretty` in `runCli` of core-ts, the `Cli.Terminal` reference in core-effect, and `CliOptions::pretty` in core-rust (`cliMain`, `NodeCli` and `cli_main` set them from standard output). The exit codes and the streams are the same in each form of the output.

### Human output

- **Off by default.** Without the output option, the command line writes JSON only, also on a terminal.
- **As an agent or in a script,** pass the JSON flag of the program if it has one, for example `--json` or `--output json`. The help of the program lists its output flags.
- **Turn it on** with the output option: `output: { flags, default, formats }` in the options of the command line in core-ts and in `Cli.Options` in core-effect, and `CliOptions::output(CliOutput::new().values(…).switch(…).default_form(…).formats(…))` in core-rust.
- **Output flags.** Each one has `names` (`--word` or `-x`) and either `form`, for a switch (`{ names: ["--json"], form: "json" }`), or `values`, for a flag with a value (`{ names: ["--format", "-f"], values: { text: "human", json: "json" } }`).
  - An output flag can be anywhere in the arguments before a `--` that is not the first argument. The last one wins.
  - For a command of the application, an output flag comes before the name of the command. The command gets the arguments after its name unchanged, and reads the chosen form from `io.output` in core-ts, `Cli.outputForm` in core-effect and `io.form` in core-rust.
  - A value that is not known exits with 3. The help and the message list the values in code point order (`--format <json|text>`).
  - An output flag can take `-h`. It cannot take `--help`, `--version`, `--cursor`, `--max-age-ms`, a flag alias, a flag of an input, or in core-effect a flag of `effect/cli` (`--log-level`, `--completions`) or a global flag: the command line stops with an error when it starts.
- **Default form.** `default` is `"json"` (the default: JSON unless an output flag chooses the human form) or `"auto"`. With `"auto"`, the form is human only when standard output is a terminal, `CI` is not set, and no coding agent is detected (`CLAUDECODE`, `CODEX_THREAD_ID`, `CURSOR_AGENT`, `AI_AGENT` and other variables).
- **Formatters.** Without a formatter, the human form prints a generic layout of the value. For a better text, give a formatter for a capability, its failures or an event, typed from its object, in `formats`:
  - core-ts: `[cliFormat(statusGet, { value: (status, ui) => …, failures: { Offline: (failure, ui) => … } }), cliFormat(statusChanged, (payload, ui) => …)]`
  - core-effect: `[App.format(statusGet, …)]`
  - core-rust: `CliFormats::new().capability(&status_get, |status: &Status, ui| …).failure(&status_get, |failure: &StatusFailure, ui| …).event(&status_changed, |status: &Status, ui| …)`
  - A formatter gets the value decoded from JSON with the schema, so it works the same with `remote`. `ui` has `bold`, `dim`, `ok`, `warn`, `error` and `table`, which write color only on a terminal.
  - If the value does not decode or the formatter fails, the generic layout is printed. Two formats for one id, or a format for an id outside the view, stop the command line when it starts.

## WebMCP

- Use WebMCP to give a browser agent the capabilities of a web page: the agent calls them in the page, with the session and the sign-in of the person, and does not read the screen. Add the binding `webmcp` to the target of the page.
- The page registers one tool for each available capability, on `document.modelContext` or `navigator.modelContext`. With no host, the binding does nothing. core-ts: `installWebMcp(session)`. core-effect: `WebMcp.install(session)`, or `Handles.open(…, { webmcp })`. core-rust has no WebMCP, because WebMCP runs in a page.
- The tools follow availability. The page can observe the status (`loading`, `reconciling`, `ready`, `failed`, `closing`, `disposed`), try a failed update again, and remove all tools while the session stays open.
- `acid-cat conform --webmcp <url>` tests the binding of a core with a page that serves the conformance fixture, in Chromium with a test host. It does not test the page of your application: test that page in a browser with a test host, as `examples/aircon/test/webmcp-page.test.ts` does.
- WebMCP serves no events. The page follows events through the TypeScript binding.

## GraphQL subscription from an event

A GraphQL API is application code, beside the bindings. A subscription field can follow an event through an event handle:

```ts
subscription: {
  statusChanged: {
    subscribe: (_, __, { session }) => session.eventHandle(statusChanged).subscribe({}), // core-ts
    resolve: (occurrence) => occurrence.data,
  },
}
```

- Return the promise of `subscribe`. It rejects with a `CallFailureError` when the subscription cannot start. GraphQL calls `return()` of the iterator when the client ends the subscription. In core-effect, use `session.event(statusChanged).subscribe({})` of `Handles.open`.
- Through server-sent events (GraphQL Yoga, the graphql-sse client), the request has one session. Keep it open until the stream ends, and close it when the client cancels the stream: then each subscription of the session is complete.
- Through WebSockets (graphql-ws on a `ws` server), make each connection one session: open it in `onConnect`, and close it in `onClose`. Refuse a connection from an origin that the API does not allow.
- `examples/aircon/apis/graphql.ts` does both, with Pothos and one schema.

## Other APIs that follow an event

- **Cap'n Web.** Take a function of the client: `followStatus(listener: RpcStub<(status: Status) => void>)`. Subscribe with a signal, keep `listener.dup()`, because Cap'n Web disposes the stubs of the parameters when the call returns, and call it with the data of each occurrence. Return an `RpcTarget` whose `[Symbol.dispose]()` aborts the signal: the client disposes it to stop. Also abort when `onRpcBroken` fires or a call to the listener rejects. A call back to the client needs a connection that stays open: serve it through WebSockets, with one session for each connection. Do not return a `ReadableStream` for this: when the client cancels it while the server waits for the next occurrence, Cap'n Web does not cancel the source.
- **Elysia.** Use a generator route and `sse`. Pass `request.signal` to `subscribe`: Elysia calls `return()` of the generator when the client goes away, but that call waits until the `await` of the loop ends. Elysia sends the response after the first value of the generator, so yield a first event at once, for example `sse({ retry: 1000 })`. Open the session in the generator with `await using`: it closes when the stream ends. For a WebSocket, use `.ws()` on a server adapter that serves WebSockets, for example `@elysiajs/node` on Node.js: open a session and subscribe in `open`, and abort the subscription in `close`. The `listen` callback of `@elysiajs/node` gives the server, with `stop()`.
- `examples/aircon/apis/capnweb.ts` and `examples/aircon/apis/elysia.ts` do this, with their tests.
